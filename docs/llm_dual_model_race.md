# Dual-Model Racing в llm_service

## Проблема

Текущий `llm_service` шлёт NER-запрос в один провайдер (ALFA, модель
`deepseek-ai/DeepSeek-V4-Flash-0731`) и ждёт ответ. Это даёт:

- **Один источник отказа** — если провайдер недоступен или возвращает пустой
  ответ, запрос падает.
- **Фиксированную латентность** — скорость ограничена самым медленным звеном,
  нет выбора между быстрым и надёжным провайдером.

Исследование публичного API DeepSeek показало, что модель `deepseek-flash`
(V4.1-Flash) отвечает в 3–5 раз быстрее ALFA (2.5–4.7s против 12–15s) и даёт
отличное качество NER, но у неё есть известный сбой: при `max_tokens=1024` она
иногда возвращает **пустой ответ** (тратит токены на reasoning и не успевает
выдать JSON). Поднятие `max_tokens` до 4096 устраняет проблему.

## Решение: гонка двух моделей (first-valid-wins)

Запрос отправляется **одновременно** в оба провайдера. Отвечаем результатом
**первой модели, вернувшей валидный результат**. Это даёт:

- **Минимальную латентность** — побеждает более быстрый провайдер.
- **Отказоустойчивость** — если один провайдер упал или вернул пусто, отвечает
  второй.
- **Маскирование сбоя** — пустой ответ `deepseek-flash` не роняет запрос:
  если он «победил» по времени, но вернул пусто, берём результат ALFA.

### Архитектура

```
                    ┌─────────────────────────────┐
                    │      llm_service            │
                    │                             │
  POST /process ──► │  extract_entities_race()    │
  WS /ws            │                             │
                    │   ┌──────────┐  ┌─────────┐ │
                    │   │ client   │  │ client  │ │
                    │   │ ALFA     │  │ DeepSeek│ │
                    │   └────┬─────┘  └────┬────┘ │
                    │        │             │      │
                    └────────┼─────────────┼──────┘
                             │             │
              ALFA (SSE)     │   DeepSeek  │
   https://alfagen...        │   https://api.deepseek.com/v1
   deepseek-ai/...-0731      │   deepseek-flash
   max_tokens=1024           │   max_tokens=4096
```

### Логика гонки

```python
async def extract_entities_race(text: str) -> list[Entity]:
    tasks = {
        asyncio.create_task(_extract(_client_alfa, ALFA_CFG, text)): "alfa",
        asyncio.create_task(_extract(_client_ds, DS_CFG, text)): "deepseek",
    }
    done, pending = await asyncio.wait(tasks, return_when=asyncio.FIRST_COMPLETED)
    for t in pending:
        t.cancel()  # освобождаем проигравшего
    for t in done:
        try:
            return t.result()  # первый валидный результат
        except Exception:
            continue  # пустой/битый ответ — пробуем следующего
    raise ValueError("Обе модели не вернули валидный результат")
```

Ключевые моменты:

- **`FIRST_COMPLETED`** — ждём первого завершившегося, не блокируясь на втором.
- **`t.cancel()`** — отменяем проигравшего, чтобы не тратить ресурсы и
  соединения.
- **First-valid-wins** — если победитель вернул пустой/невалидный результат
  (известный сбой `deepseek-flash`), переходим к следующему завершившемуся.
  Это и есть «первый валидный», а не «первый по времени».
- **Два независимых клиента** — у провайдеров разные `base_url`, `api_key` и
  `verify_ssl`, поэтому нужны отдельные `httpx.AsyncClient`.

### Конфигурация (`.env`)

```env
# Провайдер ALFA (текущий)
LLM_BASE_URL=https://alfagen.alfabank.ru/continue-dev/
LLM_API_KEY=...
LLM_MODEL=deepseek-ai/DeepSeek-V4-Flash-0731
LLM_VERIFY_SSL=false

# Провайдер DeepSeek (новый, публичный)
DS_BASE_URL=https://api.deepseek.com/v1
DS_API_KEY=...
DS_MODEL=deepseek-flash
DS_MAX_TOKENS=4096
DS_VERIFY_SSL=true
```

### Наблюдаемость

Добавляется Prometheus-счётчик `llm_race_winner{provider="alfa|deepseek"}`,
чтобы видеть, какой провайдер чаще побеждает, и `llm_race_total` для числа
гонок. Это позволяет тюнить конфигурацию (например, отключить один провайдер,
если он почти никогда не выигрывает).

### Компромиссы

- **Стоимость**: каждый запрос оплачивается дважды (оба провайдера). Для NER
  это приемлемо, т.к. объём невысок.
- **Сложность**: два клиента и логика гонки. Компенсируется выигрышем в
  латентности и надёжности.
- **Длинные тексты**: `deepseek-flash` на очень длинных документах медленный и
  нестабильный (14.7s, 2/4). Гонка это смягчает — ALFA может выиграть на таких
  текстах. Полное решение — чанкинг, вне рамок этой задачи.
